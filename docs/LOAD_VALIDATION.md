# 부하 검증 정책 — 로컬 MinIO가 상한이다

## 결정

**이 프로젝트는 실제 S3(또는 R2)에 붙여 검증하지 않는다.** 검증의 상한은 로컬 MinIO다.

인디 프로젝트이고, 실 클라우드 계정에서 의미 있는 기간·규모의 부하를 거는 비용을 감당할 계획이
없다. 앞선 리뷰들이 게이트로 적어 둔 "실제 S3 + 목표 사양에서 최소 24시간 지속 부하"는 이 결정에
따라 **폐기**하고, 아래의 로컬 검증으로 대체한다.

중요한 것은 이 대체가 무엇을 잃는지 분명히 아는 것이다. "MinIO도 S3 호환이니 같다"는 말은 사실이
아니다. 아래에 무엇이 검증되고 무엇이 검증되지 않는지를 나눠 적는다. 검증되지 않는 축은 남은
위험이며, 없어진 위험이 아니다.

---

## 무엇이 실제로 검증되는가

MinIO는 `object_store`의 `AmazonS3` 코드 경로를 그대로 태운다. 인메모리·`file://` 백엔드가
전혀 건드리지 않는 다음 항목들은 **진짜로 검증된다.**

| 항목 | 왜 로컬로 충분한가 |
|---|---|
| S3 wire 프로토콜 (SigV4 서명, path-style/virtual-hosted 주소) | 프로토콜은 구현이지 규모가 아니다. 맞거나 틀리거나 둘 중 하나다 |
| **manifest CAS** (`If-Match`/`If-None-Match` 조건부 PUT) | 이 엔진의 정합성이 통째로 여기 걸려 있다. `OBJECT_STORE_CONDITIONAL_PUT=etag`로 M7에서 동작 확인 완료 |
| multipart upload 경로 | part 크기가 임계값을 넘으면 로컬에서도 동일하게 탄다 |
| 실제 소켓 왕복, 커넥션 풀, HTTP 에러 → `object_store::Error` 매핑 | 인메모리 백엔드는 이 매핑을 전혀 타지 않는다 |
| parquet + 사이드카의 바이트 단위 왕복 | 업로드한 것과 복원한 것이 같은지는 백엔드와 무관하다 |
| eviction → restore 왕복 | 캐시 상한을 작게 잡으면 로컬에서 얼마든지 강제할 수 있다 |
| writer fencing, retention, merge, graceful shutdown | 전부 manifest CAS 위에 서 있으므로 위 항목이 검증되면 함께 검증된다 |

**엔진 자체의 규모 특성도 로컬에서 검증할 수 있다.** part 수가 수만 개일 때의 시작 시간,
flush 지연, 쿼리 계획 시간(P1-11), 테넌트 수에 비례하는 row group 파편화(N3) — 이것들은
백엔드가 아니라 **데이터 양과 실행 시간**의 함수다. 로컬에서 오래·많이 돌리면 그대로 재현된다.
지금까지 하지 않았을 뿐이다.

---

## 무엇이 검증되지 않는가 (남은 위험)

### R1. 지연 분포의 꼬리

루프백 MinIO의 왕복은 1 ms 미만이고 분포가 거의 평평하다. 실제 S3/R2는 p50이 수십 ms,
p99가 수백 ms~수 초이며 꼬리가 두껍다. ack 경로는 오브젝트 스토어를 타지 않으므로 영향이 없지만,
**flush·merge·retention·restore는 전부 영향을 받는다.** 특히 캐시 미스 쿼리(restore)의 p95는
로컬 측정치가 아무 의미가 없다.

**완화:** Tier B의 `LatencyFaultStore`가 정확히 이 축을 위해 존재한다. `LATENCY_MS`,
`LATENCY_JITTER_MS`, `READ_LATENCY_MS`로 실제 S3에 가까운 지연을 주입해 돌린다. 주입된 지연은
실측이 아니라 가정이지만, "지연이 이 정도일 때 백로그가 유계인가"라는 질문에는 답할 수 있다.
Tier B와 Tier C는 서로를 대체하지 않는다 — **Tier C가 프로토콜을, Tier B가 꼬리를 검증한다.**

### R2. 스로틀링 (가장 큰 미검증 위험)

S3는 prefix 단위로 요청률을 제한한다(대략 PUT 3,500/s, GET 5,500/s). 초과하면
`503 SlowDown`이 온다. R2도 자체 한도가 있다. **MinIO는 로컬에서 절대 스로틀하지 않는다.**

이 엔진에는 구조적으로 위험한 지점이 하나 있다. **manifest는 단일 키이고 flush마다 통째로
재작성된다**(P1-11). 이것은 교과서적인 hot-key 패턴이다. flush 주기가 기본 5초라 단일 인스턴스
정상 운영에서는 문제가 안 될 가능성이 높지만, 그 판단은 측정이 아니라 추론이다.

**완화 없음.** 이것은 첫 실 배포에서 관찰해야 하는 항목이며, 아래 "첫 실 배포 절차"에 넣었다.

### R3. 비용

이 프로젝트의 설계는 R2 Class A 비용에 지배당해 왔다(테넌트별 객체 분할을 폐기한 이유가 그것이다,
[`MULTI_TENANCY_DESIGN.md`](MULTI_TENANCY_DESIGN.md)). MinIO는 비용 신호를 전혀 주지 않는다.

**부분 완화:** 금액은 못 재도 **연산 횟수는 로컬에서 잴 수 있다.** flush 1회·merge 1회·retention
1회당 PUT/GET/LIST가 몇 번인지는 백엔드와 무관하다. 이것을 세면 요금표를 곱하는 것만 남는다.
현재 그 계측이 없다 — `todo.md`에 남겨 두었다.

### R4. 제공자별 조건부 PUT 시맨스 차이

S3, R2, MinIO의 조건부 PUT 동작은 세부가 다르다(R2는 비교적 최근에 지원이 붙었고, `object_store`가
백엔드별로 다른 옵션을 요구한다). MinIO에서 CAS가 동작한다는 것이 R2에서 동작한다는 뜻은 아니다.

**완화:** 배포 대상 스토어에서 **최소한 CAS만은** 반드시 확인한다. 부하가 아니라 기능 확인이므로
몇 분이면 되고 비용도 사실상 0이다. 아래 절차의 1단계다.

### R5. 실 네트워크 장애 양상

DNS 실패, TLS 핸드셰이크 실패, 연결 리셋, 부분 응답 — Tier B의 인프로세스 주입은 이것들을
`object_store::Error`로 흉내 낼 뿐 와이어에서 재현하지 않는다.

**완화:** 엔진의 방어는 백엔드와 무관하게 동작한다(무한 재시도 + health 게이팅 + backpressure).
장애 *종류*보다 장애 *지속*에 대한 반응이 중요하고, 그것은 Tier B로 검증된다.

## 로컬 검증 절차

### Tier B — 지연·장애 주입 (`scripts/run_load_local.sh`)

`file://` 위에 `LatencyFaultStore`를 씌워 실 S3에 가까운 지연과 오류율을 준다. 시드가 고정돼
있어 재현 가능하다. **R1과 R5를 담당한다.**

### Tier C — 실 S3 프로토콜 (`scripts/run_load_s3.sh`)

`docker compose`로 MinIO를 띄우고 `s3://` URL로 붙는다. **프로토콜과 manifest CAS를 담당한다.**

### Tier D — 지속·규모 (신규, 미실행)

기존 두 티어는 수십 초짜리다. 남은 축(P1-11의 O(N) 경로, N3 파편화, 장시간 누수)은 **시간과
양**의 문제이므로 로컬에서 그대로 잴 수 있다. 초기 목표값:

| 항목 | 값 | 이유 |
|---|---|---|
| 지속 시간 | 2시간 이상 연속 | 메모리 누수와 백로그 추세가 드러나는 최소 길이. 24시간이 이상적이나 인디 프로젝트의 반복 주기에 맞지 않는다 |
| part 수 도달 | 10,000개 이상 | 시작 시간·flush 지연·쿼리 계획 시간이 part 수에 선형인지 보는 축(P1-11) |
| 테넌트 수 | 500개 이상 | row group 파편화(N3)가 드러나는 규모 |
| 재시작 | 런 중 최소 1회 | 그 part 수에서의 시작 시간 실측 |

### 수용 기준

머신이 목표 사양(4 vCPU / 16 GiB)이 아니므로 **절대 수치는 게이트가 아니라 기록**이다. 게이트는
행위 불변량이다.

- [ ] ack된 데이터의 유실 0 (재시작 후 replay로 확인)
- [ ] WAL backlog 유계 — 상한을 넘으면 429가 나오고, 부하가 걷히면 해소된다
- [ ] RSS가 설정한 상한 아래에서 안정 (증가 추세 없음)
- [ ] flush·merge·retention이 전부 진행 중 (`*_success_total`이 증가, `*_errors_total`이 정체)
- [ ] eviction → restore 왕복 성공, restore 오류 0
- [ ] graceful shutdown이 무손실 (M6 리허설)
- [ ] 두 인스턴스를 같은 prefix에 띄우면 구 인스턴스가 fence되고 비정상 종료
- [ ] p50/p95/p99·RSS·part 수·시작 시간을 **기록** (판정하지 않음)

결과는 `docs/M7_LOAD_RESULTS.md`와 같은 형식으로 남기고, 판정과 함께 머신 프로파일·빌드
리비전·시드를 반드시 적는다. 목표 사양이 아닌 머신의 수치를 목표 대비 합격으로 적지 않는다.

## 첫 실 배포 절차

로컬 검증이 끝났다고 위 R1~R5가 사라지지 않는다. 실제로 처음 붙이는 시점에 다음을 순서대로 한다.

1. **CAS 기능 확인 (R4).** 배포 대상 스토어에 빈 prefix로 인스턴스를 띄우고, flush가 두 번 이상
   성공해 manifest `generation`이 전진하는지 본다. 실패하면 `OBJECT_STORE_CONDITIONAL_PUT`
   설정을 먼저 잡는다. **CAS 없이 운영하면 안 된다** — manifest lost update가 곧 데이터 손실이다.
2. **소규모 카나리 (R1).** 실 트래픽의 일부만 흘리며 `remote_restore_latency_ns_total`과
   `flush_errors_total`을 본다. 로컬 측정치와 자릿수가 다르면 `flush_max_interval`과
   캐시 상한을 그 자릿수에 맞춰 다시 잡는다.
3. **스로틀 관찰 (R2).** `flush_errors_total`의 증가가 `503`/`SlowDown`과 함께 오는지 확인한다.
   온다면 flush 주기를 늘리는 것이 1차 대응이고, 근본 대응은 manifest를 세대별 delta +
   주기적 스냅샷으로 바꾸는 것이다(P1-11).
4. **비용 확인 (R3).** 첫 청구 주기를 반드시 확인한다. 로컬 연산 횟수 계측이 있다면 그 예측치와
   대조하고, 없다면 이 시점이 계측을 붙일 이유가 된다.

이 네 가지가 확인되기 전까지는 **운영 중인 관측 데이터의 유일한 사본을 이 엔진에 두지 않는다.**
